RH

Robert Howe

OPTIMIZATION RESEARCH · SENSOR-PLACEMENT FORMULATION
Internship complete
Project
Manzanillo — Optimization & Solvers track (paired with Scott's Quantum Backend stream)
Repository
quantum_sensor_placement_research — synthetic-graph generator, exact MIS solver, MIS-QUBO validation, scaling experiments, illustrative port conflict graph
Contribution
Reproduced and validated the inherited budget-constrained QUBO sensor-placement implementation, then questioned whether the problem is naturally a Maximum Independent Set (MIS) rather than a budget-constrained QUBO — and built the research baseline needed to test that question.
Status
Exploratory research baseline — validated on synthetic graphs only, not yet on real port data
Key technical decision
MIS is only a natural formulation when graph edges encode genuine pairwise incompatibility — coverage overlap, redundancy, deployment restrictions, communication limits — not merely to fit a solver. Adding edges just to force an MIS shape risks distorting the original budget-constrained objective.
Known issues / open questions
Real candidate-location and coverage data still needed; no documented edge-generation procedure yet; no direct comparison against the inherited implementation on identical data; no Pasqal hardware/emulator run tied to a validated graph; no sensitivity analysis across thresholds, penalties or seeds.
DocumentationFinal Technical Report · Technical Findings (27 Jul 2026) · TECHNICAL_FINDINGS.md / METHODOLOGY.md / HANDOFF.md in-repo · weekly update slides
SR

Scott Rowekamp

QUANTUM BACKEND · MODULAR OPTIMIZATION PIPELINE
Internship complete
Project
Manzanillo — Optimization & Solvers track (paired with Robert's research stream)
Repository
Quantum_Backend — backend.py, qubo.py, pulser_sequence.py, layout.py, test_backend.py
Contribution
Built a modular SolverBackend behind one interface — classical brute-force, a Pasqal-style MIS solver, and a Zircon-style greedy solver — then extended the Pasqal path end-to-end: QUBO → MIS conflict graph → blockade-safe atom layout → real Pulser sequence → local emulator execution.
Status
Classical + Pasqal-emulator path runs end-to-end and is tested; real hardware and Zircon/Licitar API integration still pending
Key technical decision
One SolverBackend dispatcher (run_solver(backend, Q, mode)) spans classical, quantum-inspired and hardware-bound solvers, so new solver types plug in without changing calling code — the same QUBO feeds every path.
Known issues / open items
solve_zircon is a simulated greedy-descent placeholder, not a real Licitar/Zircon API call; solve_pasqal_real has only been run on Pasqal's local emulator, never real hardware; hooks into the wider existing UruQAI framework were still being finalized at handover.

AB

Andrew Brandenburg

SPORTS ANALYTICS · SOCCER VIDEO ANALYTICS PIPELINE
Complete — handed over for reuse and multi-sport expansion
Project
Sports Analytics — computer-vision pipeline that turns raw match footage into structured, queryable performance data
Contribution
Built the pipeline end to end over 11 weeks: YOLO object detection (players/ball/referees, trained on Roboflow data) → ByteTrack tracking with persistent IDs → jersey-color team assignment and possession tracking → player/ball trajectories → homography onto a 2D pitch → SQLite and SQL Server persistence → heatmaps, team zones/hulls, and a coach-facing PlayerStatistics table (touches, distance, possession%) → a Streamlit front-end so non-technical users can upload a video and get outputs directly.
YOLOByteTrackRoboflow OpenCVSQLiteSQL Server Streamlit
Status
Full pipeline runs end-to-end and was demoed via the Streamlit interface: upload a clip, select outputs, get analysis video plus JSON/database exports. Runs on both high-quality drone footage and lower-quality handheld clips.
Repository & handoff
To retrain on a new dataset: use the provided training notebook as a baseline and swap in the new Roboflow API key/dataset download script — the rest of the process stays the same. To run as-is: use best (2).pt / last (2).pt in the training weights folder — the latest trained weights. For SQL Server: point the connection string at your own instance; the create-database query and a .bacpac file are included to stand up the schema.
Key technical decision
Root-caused a major tracking bug — object IDs exploding into the thousands — to hard-coded ByteTrack settings (lost-track buffer, matching threshold, frame rate) that stopped the tracker adapting per video. Also ran a deliberate reusability audit: detection/tracking core, drawing methods, trajectory logic, and team-assignment logic port cleanly to other sports; trained weights, the dataset, and DB schema specifics don't and need rebuilding per sport.
Known limitations
Lower-quality footage is still less reliable than clean footage, despite repeated tuning. Multi-sport adaptability is documented at the component level but untested — moving to basketball or American football will need new training data and some rework of soccer-specific logic (e.g. team/possession assumptions).
Project backlog
Done: repo structure, environment setup, player/referee detection, tracking stability, trajectories, heatmaps, team & individual possession, homography / 2D pitch mapping and video, attacking/defensive zones.
In progress: ball-detection consistency, JSON export schema, architecture documentation, camera-panning robustness, more readable match IDs, tracker comparison (ByteTrack vs. BOTSort/DeepSort/Norfair).
Planned: CSV export, extensible event data model, contested-possession detection, multi-sport platform modularization (soccer module separated from a reusable core, with American football and baseball design notes), broadcast-style tactical overlays, a combined demo dashboard, and a project webpage.
DocumentationProject Documentation Weeks 1–11 · Final presentation (Soccer Analysis Platform) · Carry-over handoff notes · Sports Analytics Platform Backlog · training notebook & dataset config

JN

Jan

WATER / FLOODING TRACK · HEAVY-RAIN FORECASTING
Model complete — pilot-ready
Project
Manzanillo — Water / Flooding / Tsunamis track
Contribution
Framed multi-hazard data (flood/rainfall from CONAGUA, seismic from CENAPRED, fire signal from MODIS/VIIRS) as a shared-boundary problem, then built a heavy-rain forecasting model: LightGBM on 53,119 records with lagged/rolling/seasonal features and cost-sensitive weighting for rare heavy-rain events.
Status
Complete and validated — ≈0.99 accuracy, F1 0.90–0.92, PR-AUC ≈0.95, ROC-AUC ≈0.99 across 1–3 day horizons. Proceeding to operational pilot, with alert thresholds set alongside operations. (The related tsunami sensor-placement work in this same track is Robert & Scott's — see their cards above.)
Key technical decision
Used cost-sensitive weighting rather than resampling to handle the rarity of heavy-rain events, validated with a time-based split so the model is never evaluated on data from before its training window.
